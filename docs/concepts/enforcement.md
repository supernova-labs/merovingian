# Enforcement — how a scope is honored, not just generated

> **Generation ≠ enforcement.** The build *generates* a scoped workspace; the database *enforces*
> the scope. A build with the wrong scope stamped in a file changes nothing about what the backend
> will return.

The security model deliberately does **not** trust the workspace. The files `build` writes are a
convenience and an index — not a boundary. The boundary is inside SurrealDB, at the record level.

## The chain of trust

```
  gh identity ──▶ build/auth service ──mints──▶ scoped JWT (id = user:<x>)
                    (holds signing key)              │
                                                     ▼
  MCP call ──authenticate(token)──▶ SurrealDB sets $auth = user:<x>
                                          │
                                          ▼
                          record-level PERMISSIONS decide each row
```

1. **Identity comes from GitHub**, resolved server-side by the build/auth service
   (`src/server/service.ts`): a gh token → a gh login → a `user` record in the tenant. The user's
   machine never holds root creds or the signing key.
2. **The service mints a scoped JWT** (`mintIdentityJwt`, `src/provider/surreal.ts`) with claim
   `id = user:<userId>`.
3. **SurrealDB verifies and binds identity.** `surreal/data.surql` declares:

   ```sql
   DEFINE ACCESS identity ON DATABASE TYPE RECORD
     WITH JWT ALGORITHM HS256 KEY "…"
     DURATION FOR TOKEN 1h, FOR SESSION 1h;
   ```

   `TYPE RECORD WITH JWT` accepts a JWT signed externally (by the service) and, via the `id` claim,
   resolves `$auth` to that **user record** (a plain `TYPE JWT` would only set `$token`, with no
   record identity). From here, the session is that user and is *subordinate to* the table
   permissions below — it cannot bypass them.

## Record-level PERMISSIONS — generated from the bucket declaration

Domain tables no longer live in a hand-written file. `surreal/data.surql` is **engine-only** (the
JWT `identity` access + the `inbox` table); the business tables and their PERMISSIONS are
**generated from the graph** by `domainSchema` in `src/graph/domain.ts` (ADR 0011) and applied by
every `deploy apply` (and dev `reset`) — idempotent `OVERWRITE`, regenerated each time, never dropped.

For every `backend: surreal` bucket, each of its `tables` gets one DDL block. The fixture's
`clients` bucket (`{ id: clients, tables: [client, contact], rowScope: account, … }`) produces, for
its `client` table (exact generator output — `client` is the **fixture's example domain**, not an
engine table):

```sql
-- generated by merovingian (ADR 0011) — bucket "clients"; regenerated on every apply, do not hand-edit
DEFINE TABLE OVERWRITE client SCHEMALESS
  PERMISSIONS
    FOR select WHERE
      account IN $auth->responsible.scope
      OR $auth->responsible[WHERE scope = NONE]->purpose CONTAINSANY bucket:⟨clients⟩.owner.lineage
    FOR create, update, delete NONE;
DEFINE FIELD OVERWRITE account ON client TYPE option<string>;
```

You see a row if **either**:

- you hold a **scoped** assignment matching the row's scope field
  (`<rowScope> IN $auth->responsible.scope` — emitted only when the bucket declares a
  `rowScope`), **or**
- you hold an **unscoped** assignment on an ancestor-or-self of the bucket owner
  (`$auth->responsible[WHERE scope = NONE]->purpose CONTAINSANY bucket:⟨<id>⟩.owner.lineage` —
  an unscoped path higher in the tree → you see everything below it). This is the only path for an
  unscoped bucket.

The `rowScope` field itself is defined `option<string>` — a row without the field simply matches
no scope (fail-closed). Bucket ids are interpolated `⟨⟩`-escaped (hyphenated slugs stay legal);
table and field names are validated as safe identifiers both in the generator and in
`validateGraph` (defense in depth — PERMISSIONS clauses cannot be parameterized).

The ancestry test uses a denormalized `lineage` field (`[self, parent, …, root]`, computed at apply
time in TypeScript) rather than a live recursive traversal — a deliberate flat-for-safety choice;
`src/graph/domain.ts` carries a `TODO` to prove the native recursive form later.

**Writes are root-only today**: the generator always emits `FOR create, update, delete NONE`, so
only governance/root (the engine, seed scripts) writes domain rows. A tenant-write policy —
letting the graph declare who may create/update — is future work.

**`inbox`** (the ambient journal/friction table — append-only content, scoped resolution,
ADR 0014):

```sql
DEFINE TABLE inbox SCHEMAFULL
  PERMISSIONS
    FOR create WHERE $auth
    FOR select, update WHERE $auth AND scope IS NOT NONE
      AND $auth->responsible->purpose CONTAINSANY scope.lineage
    FOR delete NONE;
DEFINE FIELD user    ON inbox TYPE record<user> VALUE $before OR $auth;
DEFINE FIELD kind    ON inbox TYPE "journal" | "friction" VALUE $before OR $value;
DEFINE FIELD text    ON inbox TYPE string VALUE $before OR $value;
DEFINE FIELD origin  ON inbox TYPE option<string> VALUE $before OR $value;
DEFINE FIELD at      ON inbox TYPE datetime VALUE $before OR time::now();
DEFINE FIELD scope   ON inbox TYPE option<record<purpose>>;
DEFINE FIELD resolved_through ON inbox TYPE option<string>;
DEFINE FIELD drained ON inbox TYPE option<datetime>;
```

Any authenticated identity may **append**; the `user` is stamped **server-side** on create
(`VALUE $before OR $auth` — kept intact on later writes, when root has no record `$auth`) so it
cannot be forged. Since ADR 0014 the historic `FOR select NONE` is no longer absolute: a friction
carries a **`scope`** (whose problem it is — set by the writer at birth, re-scoped by root), and
members **read and resolve within the REAL reach of their lineage** — the same
`scope.lineage` dot-access mechanism as the decision log. `scope = NONE` is the root governance
queue, invisible to every member (the pre-0014 behavior, preserved as the default).

The `VALUE $before OR $value` guards make content **immutable post-create** (`at` is fully
server-stamped — not even root backdates; imports use the field-surgery pattern). Only three
things ever change: `scope` (triage/hand-off — the update permission checks the NEW row too, so
a member re-scopes only within reach; escalation beyond happens at CREATE or via root),
`drained` (ONE stamp — root drain or local resolve) and `resolved_through` (the trace from
problem to solution). Entries are never deleted — the history stays auditable.

## The decision domain (ADR 0013) — three tables, one lookup trick

The decision domain adds three engine tables to `surreal/data.surql` (summarized DDL):

```sql
-- lookup: domain → owning purpose. Written by apply from purpose.decides;
-- reconciled on every apply (a removed domain's row is DELETED — live authorization).
DEFINE TABLE OVERWRITE decision_domain SCHEMAFULL;
DEFINE FIELD OVERWRITE owner ON decision_domain TYPE record<purpose>;

-- ratified records (jurisprudence): authored in the tenant repo's decisions/,
-- shipped by deploy (root) — never written at runtime. Tenant-wide reads.
DEFINE TABLE OVERWRITE decision SCHEMAFULL
  PERMISSIONS FOR select WHERE $auth  FOR create, update, delete NONE;
-- fields: domain, status (proposed|accepted|superseded), title, content,
-- supersedes, at, embedding (reserved for the vector-search slice)

-- in-flight log: members append via the ambient decisions MCP.
DEFINE TABLE OVERWRITE decision_log SCHEMAFULL
  PERMISSIONS
    FOR create, select WHERE $auth->responsible->purpose CONTAINSANY type::record("decision_domain", domain).owner.lineage
    FOR update, delete NONE;
-- fields: user (VALUE $before OR $auth — unforgeable), domain, text,
-- records (option<array<record<decision>>> — the applied jurisprudence), at, drained
```

**Records are tenant-wide.** Any authenticated identity may read every `decision` row; only the
deploy (root) writes them — the files in the tenant repo's `decisions/` are the source of truth.

**The log rides the domain owner's lineage.** You read — and append to — the log of a domain if
any of your `responsible` edges lands on an ancestor-or-self of the domain's owning purpose: "you
log decisions where you operate". Same lineage mechanics as the bucket PERMISSIONS above.

**Why the `decision_domain` lookup exists — scan vs dot-access.** A subquery **scan** inside a
PERMISSIONS clause (e.g. `SELECT … FROM purpose WHERE …`) runs with the **caller's** permissions —
and `purpose` is closed to record users, so it would come back empty and fail closed for everyone.
Record-pointer **dot-access**, by contrast, ignores the target table's permissions — the same
mechanism the bucket clause (`bucket:⟨id⟩.owner.lineage`, ADR 0011) already relies on. So apply
maintains the `decision_domain` lookup precisely so the permission can dot-access it
(`type::record("decision_domain", domain).owner.lineage`). This asymmetry is observed Surreal
behavior, not documented contract — `test/decision-log.test.ts` pins it as an **upgrade canary**.

**Why `create = select`.** A permission-blocked CREATE is a **silent no-op** (it returns `[]`
instead of throwing), and a CREATE's return set is filtered by the *select* permission. A laxer
create policy would let an identity write rows it cannot read back — making `[]` ambiguous
("wrote-but-can't-see" vs "blocked"). With the two clauses equal, `[]` always means
blocked-nothing-written; the `decisions` MCP checks the result and reports it as a readable error.

## Why the scope stamp in the build is not the enforcement

`resolve` may stamp `env.SCOPE` / a `SCOPE` mount on a row-scoped bucket
(`src/projection/resolve.ts` rule 4). The stamp format is `"<rowScope>:<value>"` — the bucket's
`rowScope` field paired with the granting assignment's scope, e.g. `account:north`. It is a *hint*
for the workspace's index and MCP env — **generation, not enforcement**. If it were wrong or
absent, the query the MCP runs still returns only what the `PERMISSIONS` above allow, because the
row filter runs against `$auth`, not against anything the workspace declares. The workspace cannot
widen its own access.

> The PERMISSIONS generator is live (ADR 0011): the bucket's `rowScope` is **consumed for real** by
> `domainSchema` — the generated `FOR select` clause is built from that field name, not aligned by
> convention. Generation ≠ enforcement still holds: the stamp is workspace-side affordance; the
> generated PERMISSIONS in the database are the enforcement.

## The MCP fetches a fresh token per call

The bundled MCPs (`src/mcp/surreal-data.ts`, `src/mcp/inbox.ts`, `src/mcp/decisions.ts`) hold
**no token**. On every tool call they fetch a fresh scoped JWT (`src/mcp/token-source.ts`):

- **remote/production**: `gh auth token` → `GET /token` on the build/auth service, which mints the
  JWT server-side with its signing key.
- **dev/local**: `mintIdentityJwt` locally as `MEROVINGIAN_USER`.

Then `connectWithToken` authenticates and runs the query as that identity. No long-lived token ever
sits in a file, so **expiry stops mattering** and the emitted workspace carries no reusable
credential — only a *token source*.

> Note (auth gate): a token is only accepted by a DB whose `DEFINE ACCESS identity` was provisioned
> with the SAME signing key. A **real tenant** is keyed to a private `MEROVINGIAN_JWT_SECRET` (held
> only by the build/auth service, which mints only after gh-auth), so a locally dev-minted token —
> signed with the public dev key — is **rejected by construction**. Dev/test DBs are keyed to the
> public dev key on purpose (fixtures only, no real data). The gh-auth gate that proves you *are*
> that user is the service's job; the two keys never matching is what keeps dev-mint out of prod.
> See `src/provider/surreal.ts`, `src/server/service.ts`, and `surreal/auth.surql`.

## In one line

A scoped workspace is honored because the *database* filters every sensitive row against the
authenticated `$auth` identity — the build only projects a scope; SurrealDB enforces it.
